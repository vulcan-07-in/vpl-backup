1. Security Issues
All three critical security problems must be fixed before the next match. They are not theoretical - they can be exploited with zero effort by any viewer who opens DevTools.
1.1 - Admin API key hardcoded in client-side JS bundle
[CRITICAL]  ADMIN_API_KEY visible to anyone in DevTools
scorer-client.tsx:9const ADMIN_API_KEY = "vpl_secret_2025" is declared at the top of a client component. It ships inside the browser JavaScript bundle. Anyone can open DevTools → Sources and read it. Every API call (live-score, logs, active-match) sends this key in a header, giving full write access to the live match state in Redis.// WRONG - visible to any browser
const ADMIN_API_KEY = "vpl_secret_2025";
 
// RIGHT - call a server action that holds the secret server-side
// Key lives only in .env.local and is never sent to the browserFix: Move auth to server-side Next.js middleware or a Server Action. Never expose API secrets in client-side code.
1.2 - PIN hardcoded in client-side JS
[CRITICAL]  Scorer PIN compared in browser JavaScript
scorer-client.tsx:388The PIN "2025" is compared in plain JS: if (pin === "2025"). Anyone can read the bundle in DevTools. The isAuthenticated flag is also stored in localStorage as a plain string - anyone can paste one line in the console to bypass auth entirely.// WRONG

// RIGHT

  method: 'POST',
  body: JSON.stringify({ pin })

[CRITICAL]  validateAdminRequest imported but never called
api/live-score/route.ts:44The function is imported but the actual call is missing. A comment says 'For now, we trust the client'. Combined with the exposed key, anyone on the internet can POST arbitrary JSON to overwrite your live match state in Redis with a single curl command.// WRONG

1.4 - POST /api/active-match also unprotected
[CRITICAL]  validateAdminRequest imported but not called
api/active-match/route.tsSame issue as live-score. Anyone can POST to /api/active-match and change which match is broadcast to all public viewers - or set it to null, killing the live view entirely. validateAdminRequest is imported at the top as dead code.Fix: Same fix: call validateAdminRequest() at the top of the POST handler.
1.5 - api/logs: Both GET and POST are fully open with no auth
[CRITICAL]  Audit log endpoints expose sensitive data and accept arbitrary writes
api/logs/route.tsPOST accepts arbitrary action, matchId, and details - an attacker can flood your Redis logs with fake entries or craft entries that look like real scoring actions. GET exposes your full 1000-entry admin audit log (including every override and reset) to any anonymous browser visitor.Fix: Add validateAdminRequest() to both handlers. Validate that matchId is a real match. Restrict GET to admin users only.
1.6 - auth.ts fallback key is the same as the client-side hardcoded key
[HIGH]  Server fallback = client hardcoded = security theater
auth.ts:3Server reads: process.env.ADMIN_API_KEY || "vpl_secret_2025". Client sends: "vpl_secret_2025". 5. What Works Well
These design decisions are genuinely good and should be preserved as the codebase is refactored.
StrengthsTimeline-based event sourcing for UndoStoring the complete ball-by-ball timeline and rebuilding state from scratch via rebuildState is the correct architecture for a live scorer. Undo, edit, and delete are deterministic. Most hobby cricket apps get this wrong by storing only current state.applyBallEvent is a pure functionThe engine has no side effects and fully derives state from events. This means you can extract it to scorer-engine.ts and unit test every cricket rule independently - something you should do before the knockout stage.Offline sync queue with background retryThe vpl_pending_sync_* localStorage queue with a 5-second background retry is a good resilience pattern for a live-scoring context where network drops are common. The localStorage fallback on load is also smart.Edge caching on live-score GETThe s-maxage=1, stale-while-revalidate=1 header on the Redis GET reduces Redis reads significantly for concurrent public viewers while keeping data near real-time. Correct call for a public event.UI quality and scorer UXThe iPad-optimised two-column layout, the sync status indicator, the lock/unlock mechanism, the innings break overlay, and the amber/blue visual distinction between batting and bowling are all thoughtful decisions made with the actual scorer workflow in mind.Robust team name matching in getSquadForTeamThe case-insensitive toLowerCase comparison is a good default for a sheet-sourced dataset. Just needs the punctuation normalisation step added.
